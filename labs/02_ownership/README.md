# L02｜所有权与智能指针：谁负责销毁对象（约 3 小时）

本实验要回答的是：谁拥有资源、谁只是在访问资源、什么时候转移责任、什么时候销毁对象。当前编码任务是自己实现单对象版 UniquePtr<T>，不用 std::unique_ptr 包装它。下文标准库指针的语义用于理解和对照；shared_ptr/weak_ptr 尚未提供实现脚手架。

这里给出任务和预期观察，由你编写实现。普通实验使用默认删除方式，不涉及 shared_ptr 别名构造等进阶接口。材料观看时间在四周计划中另行安排，下面 3 小时用于基线实验。

## 先理解“所有权”

**拥有资源**：负责让资源在正确的时机被释放。**借用资源**：可以访问，但不负责释放，也不自动延长它的生命。

一个对象可以只有一个 owner，却有多个借用者。unique_ptr 的“独占”指独占释放责任，不是禁止其他指针访问，也不是多线程互斥。

RAII 的意思是将资源责任交给一个对象：成功取得资源后，由它的析构负责清理。正常离开作用域、提前 return、异常被捕获前的栈展开，都可以触发局部 RAII 对象的析构；abort 等异常终止不能依赖这个清理过程。

## 三种智能指针的区别

| 问题 | unique_ptr | shared_ptr | weak_ptr |
|---|---|---|---|
| 是否拥有被管理对象 | 独占所有权 | 与同组 shared_ptr 共享所有权 | 不拥有，只观察 |
| 能否复制指针句柄 | 不能复制；可以移动 | 可以复制，增加共享 owner | 可以复制，增加观察者 |
| 复制是否复制底层对象 | 不适用 | 否，仍共享原对象 | 否 |
| 是否延长对象生命 | 是，只要仍拥有它 | 是，只要还有共享 owner | 否 |
| 如何访问对象 | 解引用或成员访问 | 解引用或成员访问 | 先 lock，取得 shared_ptr 后访问 |
| 何时销毁被管理对象 | owner 析构、reset 或被替换时 | 最后一个共享 owner 释放它时 | 不直接负责销毁对象 |
| 底层机制 | 保存指针与删除器；不要求共享计数 | 使用共享控制块管理生命周期 | 关联同一控制块，尝试取得强所有权 |
| 常见用途 | 明确的单一 owner、资源转交 | 多个独立任务共同维持生命周期 | 父子反向关系、弱缓存、异步观察 |
| 主要代价 | 通常接近裸指针；大小受删除器影响 | 控制块、引用计数更新与可能的争用 | 控制块仍需存活，lock 有获取强所有权的成本 |

上表描述普通用法，不把某种指针大小或控制块布局当成标准保证。依据：[unique_ptr 语义](https://eel.is/c++draft/unique.ptr.general)、[shared_ptr 语义](https://eel.is/c++draft/util.smartptr.shared)、[weak_ptr 语义](https://eel.is/c++draft/util.smartptr.weak)。

选型时先确认生命周期：单一 owner 用 unique_ptr；确实需要共享生命周期时再用 shared_ptr；不应延长对象生命的关系用 weak_ptr。函数若只是在调用期间借用对象，引用或裸指针通常已经足够，不必为了访问创建新的 owner。[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)

## 第一步：观察 unique_ptr 的责任转移

**准备：**为 Tracked 自己补构造、析构和计数记录，再实现 UniquePtr<T> 的函数。计数应在对象实际构造/析构时更新。下面的任务用于验证你自己的 UniquePtr；不要把资源管理委托给 std::unique_ptr。

**分别做这些操作，每次先预测再运行：**
1. 创建一个 Tracked，让自己的 UniquePtr 拥有它；不转移 owner，让它离开作用域。对象应析构一次。
2. 将 owner 移动构造到另一个 UniquePtr。源指针应为空，新指针仍指向原对象，对象没有重新构造。
3. 尝试复制自己的 UniquePtr，验证它被编译器拒绝；随后撤销错误调用，让基线继续可编译。
4. 调用 get：得到借用指针，原 owner 仍负责清理。
5. 调用 reset：原对象被清理，指针变为空；若传入新的对象，则改为拥有新对象。
6. 调用 release：得到原始指针，原 UniquePtr 变为空，但对象尚未被销毁。立即把返回的指针交给另一个自己的 UniquePtr，保证后续有人负责清理。

**要分清：**

| 操作 | owner 是否仍持有原对象 | 是否销毁原对象 |
|---|---|---|
| get | 是 | 否 |
| reset 到空 | 否 | 是 |
| release | 否，责任交给调用者 | 否 |
| 移动构造另一个 unique_ptr | 源不再持有，目标持有 | 否 |

不要用 get 返回的指针另建一个独立 owner，那会让两个删除器负责同一份资源。release 后无人接管则可能泄漏。

std::move 本身只是转换表达式类别；真正执行移动构造或移动赋值时，才发生责任转移。只写一次 std::move 表达式，并不会自动清空指针。

**完成标准：**能画出移动前后的 owner；对象只构造一次、析构一次；解释 get/reset/release 的区别。

## 第二步：观察 shared_ptr 复制的是句柄

**准备：**通过 make_shared 创建一个 Tracked，保存为 p；随后复制出 q。

**要做什么：**
1. 打印 p/q 的 get 和 use_count。它们应共享同一对象，强引用数为 2。
2. 经 q 修改对象的值，再从 p 读取。能看到修改，因为没有深拷贝底层对象。
3. 释放 p。q 仍拥有对象，强引用数变为 1，对象尚未析构。
4. 释放 q。默认删除方式下，对象这时析构。
5. 独立做一次 shared_ptr 移动构造：源变为空，但只是转交一个共享 owner，不新增底层对象，也不凭空增加 owner 数量。

**先分清三个东西：**
- shared_ptr 变量：你可以有多个，每个是一个句柄。
- 被管理对象：本实验中只有一个 Tracked。
- 控制块：同一组 shared_ptr 共用的生命周期管理数据，保存计数、删除器等实现信息。

从某个 shared_ptr 的 get 结果重新构造另一个 shared_ptr，会创建独立控制块，可能导致重复删除。复制原 shared_ptr 才能共享原来的所有权组。

**完成标准：**用单线程日志解释 2 → 1 → 0 的强引用变化，指出 shared_ptr 复制与 Buffer 深拷贝的差别。use_count 不是并发访问对象时的加锁依据。

## 第三步：weak_ptr 的 lock 不等于锁 mutex

**准备：**让 weak_ptr w 观察上一步中的对象。创建 w 不应增加强引用数量。

**要做什么：**
1. 在强 owner 仍存在时调用 w.lock，保存返回的 shared_ptr 为 hold。
2. hold 存活期间，它也是强 owner。释放原 p/q，对象仍不能析构，因为 hold 还在拥有它。
3. 释放 hold，确认对象析构。
4. 此时 w 仍然存在，但 expired 为真；再次 lock 得到空 shared_ptr。
5. 最后释放 w。观察者消失不等于这时才析构对象——对象已经在上一步结束生命。

lock 的含义是：原子地尝试取得一个强 owner。成功后，在返回的 shared_ptr 持有期间维持对象生命；失败则返回空。它不会锁住对象的字段，也不会把已经销毁的对象重新创建出来。

多线程场景中，先检查 expired 再使用不是一个原子操作；应直接 lock 并检查结果。这里的“原子”保障生命周期获取，仍不保障成员数据的并发读写。[weak_ptr::lock 契约](https://eel.is/c++draft/util.smartptr.weak.obs)

**对象与控制块是两条生命周期：**

| 阶段 | 强 owner | weak_ptr 观察者 | 被管理对象 | 控制块 |
|---|---:|---:|---|---|
| p/q 持有，w 观察 | 2 | 1 | 存活 | 存活 |
| 释放所有强 owner | 0 | 1 | 已析构 | 仍需保留供 w 查询 |
| 最后一个弱观察者也释放 | 0 | 0 | 已析构 | 可以释放 |

这是概念计数表，不是让你直接读取 libc++ 私有字段。实现可能用偏移计数和内部弱引用。

make_shared 通常把对象存储与控制块放在一次分配中。强引用归零时对象析构；若 weak_ptr 还存在，合并分配的内存通常要等控制块释放才归还。因此“对象已析构”和“那块内存已释放”是两件事。

**完成标准：**解释为何 w 的存在不保活对象，hold 却会；画出对象与控制块先后结束的过程。

## 第四步：用 weak_ptr 表达不拥有的反向关系

**准备：**两个节点 A/B。A 指向 B，B 又指向 A；先让两条边都使用 shared_ptr。

**要做什么：**
1. 外部 owner 还在时，记录两个对象的强引用数。
2. 释放外部 owner，观察两个对象是否析构。
3. 解释剩余的强引用来自哪里：它们相互持有，使计数不能归零。
4. 测试第一版时保留外部 weak_ptr，观察后通过 lock 取得临时 owner，主动清空一条强边，再释放临时 owner，完成清理。
5. 在第二版中，让 A 拥有 B，B 仅用 weak_ptr 观察 A。释放外部 owner，确认两个对象都结束生命。

重点是先决定语义：谁应该拥有谁。weak_ptr 不是任意挑一条边替换的工具；例如父节点拥有子节点，子节点的反向关联不应让父节点永久存活。

**完成标准：**用所有权图解释循环引用，并用存活计数确认第二版正常清理。不要把泄漏永久留在默认实验中。

## 第五步：自己管理资源，再比较 Rule of Zero

这一步练习的是类的拷贝/移动，不是手写完整智能指针。

**先写一个受限 Buffer：**
- 只管理一段 int 数组；记录长度、资源地址、当前未释放的数组数量。
- 长度 0 时采用空指针、长度 0 的状态。
- 普通构造分配数组；析构负责匹配的数组释放。
- 拷贝构造/拷贝赋值做深拷贝：内容相同，但资源独立。
- 移动构造/移动赋值转交资源：不逐个复制整数；源回到空状态。
- 本实验约定自赋值、自移动不改变原内容；普通移动后源对象可析构、可重新赋值。
- 拷贝赋值先准备新资源，成功后再替换旧资源；分配失败时保留原状态。失败注入作为选做，基线先解释为什么这个顺序重要。

**“Rule of Five”具体指：**析构函数、拷贝构造、拷贝赋值、移动构造、移动赋值。自管资源时，要检查这五项的行为；可以根据接口需求自定义、默认或删除，并非所有类都必须手写五项。

**验证清单：**
- 空 Buffer 析构、复制、移动。
- 两个深拷贝副本同时存在；修改其中一个不影响另一个。
- 给已经持有资源的目标进行拷贝/移动赋值，旧资源被正确释放。
- 移动后，目标拥有原资源地址；源为空；两者析构不会重复释放。
- 自赋值、自移动符合本实验契约。
- 所有作用域结束后，未释放数组计数归零。对象数量与数组数量分别记录。

**再改成成员自动管理资源：**
- 成员使用 vector<int>，观察默认生成的复制能否做到独立内容，移动如何处理资源。
- 区分本实验自己规定的 Buffer 移动后为空，与标准库的一般“有效但状态未指定”规则；不要把所有被移动对象都断言为空。
- 或使用 unique_ptr<int[]>，观察类为什么默认不能复制。自动管理释放不会自动带来深拷贝。
- Rule of Zero 是业务类不手写资源管理的特殊成员函数，把责任交给成员。不要在这一版随手加入自定义析构函数；它会影响隐式移动的生成，日志可放在资源类型或外部计数中。

**完成标准：**解释“自管 raw storage”“vector 成员”“unique_ptr 成员”三种设计的复制能力和清理责任。暂不支持任意元素类型或完整 allocator。

## shared_ptr 的线程安全边界

| 场景 | 是否由 shared_ptr 自动解决 |
|---|---|
| 不同 shared_ptr 变量共享控制块，分别复制/释放各自的句柄 | 引用计数管理支持这种并发 |
| 多个线程读写同一个 shared_ptr 变量，且有 reset/赋值等修改 | 需要额外同步；可以用 mutex 或 C++20 的 atomic<shared_ptr<T>> |
| 多个线程修改它指向的对象字段 | 需要保护对象状态；控制块计数不代替这把锁 |

weak_ptr 的 lock 和 atomic<shared_ptr<T>> 也不会自动保护对象成员；同一个 weak_ptr 变量被并发 reset/赋值与 lock 时，同样需要同步。并发只讨论边界，本实验不写含 data race 的默认测试。[shared_ptr 数据竞争规则](https://eel.is/c++draft/util.smartptr.shared)

## 与 L01 的虚析构联系起来

unique_ptr<Base> 的默认删除器通过 Base 指针执行 delete。实际对象为 Derived 时，仍需要 Base 的虚析构；智能指针不会自动修复这个类型设计。

shared_ptr 的删除方式保存在控制块中，与创建所有权时的类型和删除器有关。从 make_shared<Derived> 转成 shared_ptr<Base> 能保留 Derived 的清理方式；若先把 Derived 地址存为 Base 指针，再用它新建默认 shared_ptr，清理方式可能只知道 Base，仍需虚析构。这个区别可在源码阅读后选做验证。
