# L03｜vector 生命周期与 MiniVector：容量不等于对象数量（约 6 小时）

## 1. 先分清三个量

| 名称 | 在本实验中的含义 | 容易混淆的地方 |
|---|---|---|
| `size()` | vector 中当前有多少个元素 | 只有下标 `[0, size)` 内的元素可以访问 |
| `capacity()` | 不重新分配存储时，最多能容纳多少个元素 | 备用容量不是已经存在、可以访问的元素 |
| `Tracked::alive` | 当前进程中还活着的 `Tracked` 对象总数 | 这是全局计数；其他容器、局部对象和临时对象也会被计入 |

例如 `size = 2, capacity = 5`，可以画成下面这样。这里的 5 是概念示意，不是要求当前程序输出这个容量；运行时查看实际的 `capacity`：

```text
同一块连续存储中的槽位
下标        0          1          2          3          4
状态     [活对象]   [活对象]   [备用存储] [备用存储] [备用存储]
         <---- size ---->
         <---------------- capacity ---------------->
```

下标 2 处虽然有存储空间，仍不能通过 `values[2]` 当作 vector 元素读写。`reserve` 的作用是预留容量，`resize` 的作用是改变元素数量；两者都接收一个整数，但整数表达的需求不同。[标准容量与 resize 契约](https://eel.is/c++draft/vector.capacity)

从 L02 转过来时特别注意：智能指针的移动通常是在转交资源责任；vector **扩容**则需要让已有元素在另一块存储中继续存在。本次程序观察的是扩容时元素的搬迁，移动整个容器另留到后续学习。

## 3. 对照 observe.cpp 读日志

### Tracked 记录的是什么

先看文件开头的 `Tracked`，逐个找到它的默认构造、带整数参数的构造、拷贝构造、移动构造和析构。

| 日志列 | 怎样理解 |
|---|---|
| `size` | 容器里有多少个元素 |
| `capacity` | 当前存储能容纳多少个元素 |
| `data` | 当前元素存储的起始地址，用于观察存储是否更换 |
| `values` | 当前活元素的 `value` 列表；空容器打印 `[]`，不读取备用槽位 |
| `alive` | 构造时增加、析构时减少，表示当前存活数量 |
| `constructed` | 所有构造函数成功完成的累计次数，包括默认、整数参数、拷贝和移动构造 |
| `destroyed` | 析构函数被调用的累计次数 |
| `copies` | 自程序启动以来，拷贝构造被调用的累计次数 |
| `moves` | 自程序启动以来，移动构造被调用的累计次数 |

`constructed/destroyed/copies/moves` 都是累计值，不会因为对象析构而清零。要知道某一步发生了多少次搬迁，应比较相邻日志的**差值**，而不是只看累计值。`constructed - destroyed` 应等于 `alive`；扩容前后 `alive` 不变时，仍可从构造与析构的增量看出对象更替。

`constructed` 记录对象构造，不是存储分配次数；`destroyed` 记录对象析构，不是存储释放次数。这份程序没有自定义 allocator，也不打印分配/释放事件。

当前 `Tracked` 的移动构造只复制一个整数，也没有清空源对象的 `value`，但调用的仍然是移动构造函数。不要把“移动”理解成源对象必须变成某个固定值；被移动的旧对象仍需要结束生命周期。

1. 第一次 `reserve(2)` 没有增加 `alive`，为什么仍然有意义？容量至少为 2，不要求恰好为 2。
2. 当前两次 `emplace_back` 用整数参数直接构造元素，不需要先创建一个外部 `Tracked` 再复制进去。为什么此时搬迁计数不增加？

4. `resize(4)` 会新增两个默认构造的元素。**是否还要搬迁旧元素，取决于第二次 `reserve` 后的实际容量是否足够。** 不要预设这一步必然扩容，也不要预设必然不扩容。
5. `clear()` 后容量保留，但原来的元素已经结束生命周期。为什么不能继续读取下标 0，即使地址看起来没有变？

## 4. 改变一个条件：理解 noexcept 与失效

### 实验 A：移动构造不再承诺 noexcept

保留原版输出，再只去掉 `Tracked` 移动构造上的 `noexcept`，保留它的拷贝构造。重新构建并运行，重点比较第二次 `reserve` 前后的 `copies/moves` 差值。

去掉 `noexcept` 表示移动构造**可能**抛异常，不等于你已经让它实际抛异常。这里先观察标准库如何选择搬迁方式，不同时加入失败注入。

要解释的是：如果移动到一半失败，部分旧元素可能已经被改动；如果可以复制，保留旧值会怎样帮助容器维持“失败后原状态不变”的保证？具体选择结合本机日志和源码核对，不把“移动总比拷贝优先”当规则。[reserve 异常保证](https://eel.is/c++draft/vector.capacity)

完成后恢复基线的 `noexcept`。纯拷贝类型作为选做：可以只提供拷贝构造而不声明移动构造，先弄清它和显式删除移动构造的区别，再用于观察。

### 地址、引用和 iterator 为什么会失效

先运行新增的 [iterators.cpp](iterators.cpp)，它使用 `vector<int>`，从基本语法开始演示。本例只调用标准容器，不提供 MiniVector 的实现。

```sh

./build/debug/vector_iterators
ctest --preset debug -R '^vector_iterators$' --output-on-failure
```

如果尚未配置 Debug，先执行第 2 节的 `cmake --preset debug`。

**先认识迭代器的基本操作：**

| 表达式 | 对 `vector<int> v{10, 20, 30}` 的含义 |
|---|---|
| `v.begin()` | 指向第一个元素 10；空容器的 begin 等于 end |
| `v.end()` | 最后一个元素之后的位置，不能解引用 |
| `auto it = v.begin()` | 保存当前第一个元素的位置；auto 推导出迭代器类型 |
| `*it` | 访问当前位置的元素，例如读取 10；这是解引用 |
| `++it` | 前进一个位置，例如从 10 前进到 20 |
| `v.begin() + 1` | 第二个元素的位置；vector 支持这种随机访问 |
| `it != v.end()` | 检查遍历是否到达尾后位置；it 必须是当前有效的迭代器 |
| `v.end() - 1` | 非空 vector 的最后一个元素的位置 |

`insert` 接收的是**插入位置的迭代器**，在这个位置之前插入，并返回指向新元素的迭代器。`erase` 删除迭代器指向的元素，返回后继元素的新位置；如果删除的是最后一个元素，则返回新的 `end()`。

下面是一段基本用法，完整的输出与检查在 `iterators.cpp` 中：

```cpp
std::vector<int> v{10, 20, 30};
v.reserve(8);                     // 保证接下来的这次插入不扩容。

auto position = v.begin() + 1;     // 指向 20。
auto inserted = v.insert(position, 15);
// v 现在是 [10, 15, 20, 30]。旧 position 失效，不再使用。
// *inserted 是 15，这是 insert 返回的有效迭代器。

auto next = v.erase(v.begin() + 2); // 重新获取位置，删除 20。
// v 现在是 [10, 15, 30]。*next 是 30。
```

注意 `insert/erase` 的位置参数不是下标：需要第几个位置时，用 `begin() + 下标`；删除单个元素时不能传入 `end()`。上面的代码每次根据操作后的容器重新取得位置，不继续使用失效的旧位置。

程序还演示了三件事：追加且不扩容时，指向已有元素的迭代器仍可使用，但要重新获取 end；强制扩容后重新获取 begin；遍历删除偶数时使用 `it = v.erase(it)`，删除分支不再额外递增，避免跳过后继元素。失效的旧迭代器没有被解引用或拿来比较。

iterator 是容器中位置的表示，引用和元素指针也依赖元素的生命周期。`end()` 表示元素区间之后的位置，不能解引用。即使已有元素没有移动，追加后原来的 `end()` 也会失效。

先理解下面的规则，再为其中两种情形画图；`insert/erase` 只需学习标准 vector 的行为，暂不加入 MiniVector 的接口。

| 操作 | 原有元素的指针、引用和迭代器 | 原来的 `end()` |
|---|---|---|
| `reserve(n)`，`n <= capacity` | 保持有效 | 保持有效 |
| `reserve(n)`，`n > capacity` | 全部失效 | 失效 |
| `push_back/emplace_back`，没有重分配 | 原有元素的保持有效 | 失效 |
| `push_back/emplace_back`，发生重分配 | 全部失效 | 失效 |
| 非空 `insert`，没有重分配 | 插入位置之前的有效；该位置及之后的失效 | 失效 |
| 非空 `insert`，发生重分配 | 全部失效 | 失效 |
| 非空 `erase` | 删除位置之前的有效；该位置及之后的失效 | 失效 |
| `clear` | 原有元素的全部失效 | 失效 |

规则依据：[reserve](https://eel.is/c++draft/vector.capacity)、[插入与删除](https://eel.is/c++draft/vector.modifiers)、[clear](https://eel.is/c++draft/sequence.reqmts)。运行只能观察具体路径，不能用“旧地址还能读出值”推翻失效规则。

**第一阶段完成标准：**能解释第 3 节的八行基线和实验 B 的三个场景，分清 `reserve/resize/clear`，并说明为何去掉 `noexcept` 可能改变搬迁方式。做到这里，再开始手写容器。

## 5. 写 MiniVector 前，先理解存储与构造

原说明中的 “raw storage” 指的是供元素使用的存储空间；本实验需要分别管理空间和元素生命周期。

| 工具 | 负责什么 | 不负责什么 |
|---|---|---|
| `std::allocator<T>` 的分配操作 | 获得能容纳指定数量元素、满足对齐要求的存储 | 不逐个构造元素 |
| `std::construct_at` | 在某个可用槽位构造对象 | 不为整个容器分配容量 |
| `std::destroy_at` | 结束一个已构造对象的生命周期 | 不归还整块存储 |
| allocator 的释放操作 | 归还匹配的存储，分配数量与释放数量须对应 | 不替你逐个析构活元素 |

这些工具来自 C++20 可用的 `<memory>`。先阅读它们各自的接口要求，再决定如何在你的类中使用。[分配与释放](https://eel.is/c++draft/allocator.members)、[构造](https://eel.is/c++draft/specialized.construct)、[析构](https://eel.is/c++draft/specialized.destroy)

不要用 `new T[capacity]` 代替这套区分：它会建立整组数组元素，对于 `Tracked` 这样的类类型，会调用每个元素的默认构造。这会让“备用容量”和“活元素数量”混在一起，也限制可支持的元素类型。

在纸上画出你的容器状态，回答以下问题后再编码：

- 哪些信息表示存储的所有权、已经构造的元素数量和容量？
- 为什么需要维持 `0 <= size <= capacity`？哪些槽位可以访问、哪些可以析构？
- `clear` 后还拥有什么？析构后应当释放什么？
- 扩容成功后和扩容失败后，分别有哪些对象、哪些存储需要负责清理？

“不变量”就是每次公开操作正常返回后必须成立的条件。对本练习来说，活元素应恰好占据 `[0, size)`，其余槽位只留作容量；所有权应清楚，不能让两个容器负责释放同一块存储。

| 默认构造 | 空状态，`size = capacity = 0` |
| `size/capacity` | 查询状态，不构造元素 |
| `reserve(n)` | `n <= capacity` 时不改变状态；否则容量至少为 n，元素数量和内容不变 |
| `push_back` | 在尾部新增一个元素；容量不足时增长；先支持拷贝追加，再支持移动追加 |
| `clear` | 销毁全部活元素，size 归零，保留容量 |
| `operator[]` | 返回已有元素的引用；调用方保证下标小于 size，不做自动扩容 |
| 析构 | 清理仍活着的元素，并释放拥有的存储 |
| 移动构造/赋值 | 转交整块资源；普通移动后源回到上述空状态；移动赋值须清理目标原资源 |
| 复制容器 | 基线显式禁止复制，元素仍可以是可拷贝类型 |

这是你的受限容器契约，尤其“移动后源为空”是本练习的约定，不推广成所有标准库对象的统一规则。自移动赋值约定保留自身内容。

按三个小任务推进，每次先写检查再扩大范围：

1. **先支持 `int`。** 做空容器、预留容量、追加、下标访问、清空和销毁。观察值与大小，不用 `std::vector` 成员代管核心存储。自动增长采用你能解释的几何增长策略，不要求复刻标准库倍率；增长计算要考虑容量上限与整数溢出。
2. **再支持生命周期可见的类型。** 使用本实验 `Tracked` 的计数思路，验证分配容量不会提前构造元素，清空后也不会提前释放容量。容量管理成功后，再加入整个容器的移动和已有资源目标的移动赋值。
3. **最后处理扩容异常。** 支持可拷贝元素，以及移动构造为 `noexcept` 的元素。把搬迁方式与它们的保证联系起来；暂不支持“不可复制且移动可能抛异常”的元素。

不要直接把 L02 和 L03 的两个 `observe/observer.cpp` 一起包含进来，它们都定义了 `Tracked`。为当前独立实验选择一个测试类型即可。

“强异常保证”指操作失败后，容器的大小、容量和元素内容保持调用前的状态，且没有新增泄漏。本练习要求 `reserve` 在支持的类型范围内提供这个保证；你的代码需要能区分“失败前已经构造的新元素”和“尚未构造的槽位”。写出成功与失败后的责任图，再自己决定实现方式。

`push_back` 的失败语义也要写清楚：基线至少应保持容器可用、不泄漏，说明是否承诺失败后容量也不变。“没崩溃”不是异常保证。

完整 allocator 传播、迭代器实现、`insert/erase/resize`、可抛异常的 move-only 元素都放到选做。先完成这些受限接口，不扩展成完整 STL 容器。

运行你自己的实验：

```sh
cmake --build --preset debug --target mini_vector && ./build/debug/mini_vector
```

`mini_vector` 是练习构建目标，没有被加入 CTest；只运行现有的 vector 观察测试不会检查你的 MiniVector。直接运行上面的程序执行 `main` 中的检查。异常检查验证对象清理和原状态；存储泄漏及非法访问还需要在正常工作的 ASan/UBSan 环境中补查。

## 7. 怎样验证自己的实现（约 1 小时）

每项写清操作、预期行为和验证结果。遇到失败先缩成最小场景，再回到所有权图查原因。

| 场景 | 应当验证什么 |
|---|---|
| 默认空容器、重复 `clear`、空容器析构 | 状态保持合法，无重复释放 |
| 空容器 `reserve(1)` | 容量足够但 size 仍为 0；没有新增活元素 |
| 在容量足够时追加 | 新值正确，size 增加，已有元素内容不变 |
| 填满容量后再追加、连续增长 | 顺序和所有值保留，size 不超过 capacity |
| 小于或等于当前容量的 `reserve` | 状态不变，不搬迁、不缩小容量 |
| `clear` 后重新追加 | 旧元素全部析构，保留容量可重用 |
| 移动构造、向非空目标移动赋值 | 内容转交，源为空，目标原元素得到清理 |
| 自移动、两个移动相关容器先后析构 | 符合契约，不丢失资源、不重复释放 |
| 扩容时复制到中途抛异常 | 新构造元素被清理；原大小、容量、值不变；旧容器仍可继续使用 |
| 所有测试作用域结束 | 活对象总数归零，存储也各自得到释放 |

失败注入用一个专门的“第几次拷贝尝试时抛异常”的测试类型，由你自己编写。只在构造成功后增加活对象计数；拷贝尝试次数与成功构造数量分开记录，否则测试本身会误报泄漏。不要在 `noexcept` 构造或析构函数里抛异常。

再用固定随机种子生成同一组 `push_back/reserve/clear` 操作，分别交给你的容器和 `std::vector<int>`。每步比较 **size 和元素值**；不要求容量一致，因为增长策略可以不同。记录随机种子和失败的操作序列，方便重现。

使用多个容器或外部测试对象时，`Tracked::alive` 应等于这些对象的存活总数，不再是某一个容器的 size。对象计数也不等于分配次数；如果要核对存储泄漏，需另记分配与释放，或在运行正常的 ASan/UBSan 环境中补查。

最后讨论一次参数别名：`push_back(v[0])` 的输入引用指向容器自己。如果追加触发扩容，输入依赖的旧元素会怎样？支持它就需要验证这一条路径；基线也可以明确约定“追加参数不得引用本容器元素”，并把补齐此行为列为后续任务。这里的限制属于你的 MiniVector，不属于标准 vector 的通用限制。
